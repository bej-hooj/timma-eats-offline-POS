## Owner decision recorded this session

**Relay confidentiality (K3c follow-up, owner-approved 2026-08-16).** The cloud relay's
`DeviceCredential` MAC gives integrity, not confidentiality: on a branch-keyed Realtime broadcast
channel every paired tablet — and anyone who can subscribe — can read its peers' order frames in
plaintext. The owner chose **lock the channel down server-side rather than encrypt the payload**.
The hub already owns this data in Supabase, so payload encryption would add key management to every
tablet to protect data the same devices are already trusted with; channel authorization is the
cheaper control at the same boundary.

Binding for K5/K9 when the real `CloudRelayBackend` lands:

1. The branch channel is **private**, authorized server-side per connection against the device key —
   not a public broadcast topic that anyone with the anon key can join.
2. A device may subscribe to **its own branch only** — the same restriction `rpc_menu_snapshot` and
   `rpc_device_transition_order` already enforce (ECOSYSTEM §23.10).
3. Frames stay signed. Channel authorization decides *who may listen*; the MAC still decides *who
   may act*, and the hub keeps verifying before it applies. Neither replaces the other.

## What K4 is

Attract loop → menu → composer → cart → confirm → **a large calm "pay at the counter" number**.
Take-away only, so there is no mode screen at all. **Four taps from attract to printed slip** is the
target and every screen not on that path has to justify itself.

## Where it lives, and why not in the customer app

A **second entrypoint in this repo**, not a second repo and not a route inside the phone app:

- `lib/kiosk_main.dart` — its own `main()`, built with `flutter build --target lib/kiosk_main.dart`.
- `lib/kiosk/` — the whole surface, importing `pos_core` and the shared design tokens.

The kiosk shares tokens, l10n and `pos_core` with the phone app and shares **nothing else**: no
auth, no Supabase session, no cart controller, no router. It is a different product on a different
device with a different customer posture. A route inside the phone app would drag the whole auth
graph onto a device that must never hold a customer session, and a second repo would fork the design
tokens on day one — which §3 forbids.

⚠ **The parallel session owns `lib/core/theme/*`, `home_screen.dart`, `category_screen.dart`, the
composer screens, `cart_controller.dart`, `kit_widgets.dart` and the router.** K4 **reads** tokens
and **writes nothing** under those paths. `KioskTheme` derives from `AppTokens`; it does not edit it.

## Design: a standing customer at arm's length

The phone app's scale is wrong here — the reference is a tablet at ~60–70 cm, not a phone at 30 cm.

- Base body type **22sp**, dish titles **28sp**, the counter number **120sp**.
- Minimum touch target **72dp** (phone app: 48dp, §13.3). A standing customer taps with a thumb at
  arm's length and misses.
- One accent per screen. Motion: **1–2 animated elements per view**, 200–300 ms, per the F-pass
  rules (`design-fable-pass-2026-08-05`). The attract loop is the one place a longer, slower motion
  is allowed, because nobody is waiting on it.
- **No PII anywhere.** No name, no phone, no email — the kiosk never collects them and the screen
  faces the room.

## The rules this stage must not break

1. **`min/max` count DISTINCT options, not total quantity.** Corrected once in the webapp composer
   (`timma-webapp-composer-parity-2026-07-29`) and stated again on `SnapshotOptionGroup`. The kiosk
   composer must not rediscover it as a bug.
2. **The client never computes a price.** The UI sends `PosCartLine` (ids + quantities) and the
   pinned snapshot prices it in `PosEngine._price`. A total rendered in the cart is for the customer
   to read, never a number that reaches the engine. §0.2, §23.3.
3. **Money is integer minor units.** One formatter. A float in this stage is a review blocker (§3).
4. **Sold-out is enforced, not decorative.** `SnapshotProduct.available == false` blocks the
   composer, not just greys a badge — the four-barrier rule from the phone app.
5. **A kiosk with no pinned menu refuses loudly.** `placeKioskOrder` throws `noActiveSnapshot`; the
   UI must show that as an out-of-service screen, never an empty menu that looks like a closed
   kitchen.
6. **Idle clears the cart.** An abandoned basket must never become the next customer's order.
7. **No hardcoded user-facing text** — every string through l10n, FR and EN complete (§3).

> **RESULT — DONE 2026-08-16.** The kiosk surface ships as a second entrypoint
> (`lib/kiosk_main.dart` + `lib/kiosk/`): attract → menu → composer → cart → counter number, with
> the idle timeout, an FR/EN toggle and an out-of-service refusal. **App suite 364/364** (11 new
> kiosk tests), `flutter analyze` clean on the kiosk and its test. Nothing under the parallel
> session's paths was touched.
>
> Proven against a **real `pos_core` engine on an in-memory store**, not a mock — the whole point of
> this surface is that it prices and places locally, so a fake engine would prove nothing. The tests
> assert the placed order's total out of the store, which is what makes "the client never computes a
> price" checkable rather than aspirational.
>
> **Two defects the tests caught while being written:**
>
> - **The cart's bottom bar overflowed by 83 px at the real kiosk width** (1200×800 logical,
>   landscape). Label + total + two kiosk-sized buttons side by side do not fit; on the tablet that
>   is a customer who cannot see the *Commander* button. The total is now stacked and flexible.
>   Sizing a layout at phone widths and assuming it scales up is exactly the trap `KioskScale`
>   exists to name.
> - **The looping attract animation makes `pumpAndSettle` hang forever.** Rather than special-casing
>   the tests, they drive the `disableAnimations` accessibility flag the screen already honours —
>   which means every flow test also runs the reduced-motion path a customer with vestibular
>   sensitivity gets.
>
> **Structural debt, deliberate and recorded.** `pos_core` is now a dependency of the app's pubspec
> so the kiosk entrypoint can reach it. That is free today (sqlite3 is FFI, not a plugin, and
> `flutter build` compiles from one entrypoint) but it is not where this belongs: `pos_core`'s own
> pubspec says the native SQLite lives in "the two APPS' pubspecs", and `sqlite3_flutter_libs` is
> deliberately **not** added to the customer app — shipping SQLite natives to every customer phone
> for a feature that phone does not have is the wrong trade. The kiosk and KDS should become their
> own app packages consuming a shared `timma_design` package (tokens + l10n + `TimmaMark`). That
> extraction is **blocked**: `lib/core/theme/*` has uncommitted parallel-session edits. Do it when
> that tree is clean, before K5 grows a second copy of this problem.
>
> **Not done: the device walkthrough.** Hardware-blocked — the parallel session holds the Samsung.
> Golden tests are also not written; the widget tests cover the states and goldens want a settled
> design plus a device pass to be worth pinning.
